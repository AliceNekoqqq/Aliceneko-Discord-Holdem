# Gemini 文案协作流程 v1
日期：2026-10-11（Asia/Shanghai）
状态：调用工具已实现；2026-10-11 已完成真实起草、两轮定点返修、主 agent 审核与批准导出。未改变生产游戏。

## 目标与范围
用户要求：创作文案优先由 Gemini 起草，主 agent 负责评估；不符合要求则明确反馈、重新生成，达到可用标准后才采用。
适用：角色背景、世界观、剧情、roleplay 示例、宣传文案、菜单描述、界面措辞及人设候选。代码、机制、数值、事实核验与最终整合仍由主 agent 负责。
开发时创作与线上酒馆聊天分开。日常 Discord 聊天继续现有调用链，不默认加逐条 Codex 审核，不自动替换线上人设。

## 职责与任务流程
1. 主 agent 编制 brief：目的、受众、展示位置、字数、语气、必需信息、禁止内容、已确认设定、需要保留的原文、输出格式。
2. 主 agent 只取相关项目资料。把已确定事实列为锁定项，待设计内容列为候选；不能让模型把候选当现有功能。
3. Gemini 输出正文草稿；结构化批量任务使用 item_id 与独立正文，避免标题、说明混入正式文本。
4. 本地检查长度、必需字段、占位符、命名与格式；主 agent 阅读正文审查设定、自然程度、人物动机、可读性和实际界面表现。
5. 审核返回 pass/revise/blocked，以及具体位置、原因和修改要求。不能只发“不够好，再写一次”。
6. revise 时发送原 brief、当前最佳稿和本轮问题，只重写受影响段落；已通过的条目冻结。整篇问题才整篇返修。
7. pass 后主 agent 做必要的排版/标点整理；实质改写要再审核。通过稿才进入产品文件或交付。
8. 每批保存任务与审核结果，断点恢复从最佳稿继续，不重复生成已通过内容。

## 可用标准
硬性项全部通过才可采用：用户要求、字数/格式、锁定设定、真实功能与数值、人物身份、占位符均正确。
主观项由主 agent 结合用户偏好判定，分数只辅助，不能以模型自评代替审核。
- 文案：清楚、简洁，手机上能读懂，按钮名称与实际动作一致；不把技术细节写进玩家流程。
- 人设/角色：动机具体，角色有差异，言行一致，不靠反复堆叠形容词。
- 剧情/roleplay：场景与人物动作连贯，台词自然，不替玩家决定行动或内心；不无故跳出角色解释表演，不机械追加追问。
- 世界观：与现有设定一致，候选新增事实显式标注；不得暗改已上线机制或历史。
- 宣传：只宣传真实完成的功能；未上线内容明确写为计划。
人设改写只生成候选，不借创作任务自动覆盖线上人格。

## 返修、失败与费用控制
目标始终是可用，不把未通过稿当成已完成交付。
默认每批 3 次内容调用（初稿 + 2 次返修）；批末保存最佳稿和未解决问题。仍有明确改善方向时，在当前活动工作中继续下一批，无需用户逐轮确认。
单任务默认最多 9 次内容调用作为费用熔断值；可由任务明确覆盖。达到上限或连续两次无改善时保存为 blocked，报告原因，不降标准假装通过，也不无限循环扣费。
网络失败与内容返修分别计数。认证失败、模型不存在和余额不足不盲目重试；瞬时错误遵守服务返回的等待信息，最多重试 2 次。连接中断可能已计费，记录结果未知，避免静默重复扣费。
长文按场景/角色/章节拆分，使用共享设定摘要及已通过内容摘要；不要每轮传全部仓库或完整历史。
模型与输出额度按任务配置，创作任务不能沿用日常聊天的短输出上限；截断稿不能通过审核。
对用户只汇报采用结果、必要的未解决问题及重要费用异常，不输出全部中间草稿。

## 实现与扩展
开发工具入口：docs/ai/tools/gemini-writer.mjs（已实现；使用方法见同目录 README.md）。
密钥从 GEMINI_WRITER_API_KEY 环境变量或受保护 secret 注入；不写入源码、AGENTS.md、任务文件、日志、提交或前端。
base URL 使用用户指定的 https://gcli.ggchan.dev；不把该地址当作已验证的完整请求 endpoint。
GEMINI_WRITER_MODEL 与 API 协议、完整 endpoint 独立配置。实现前仅核对现有适配器和非敏感配置，确认该网关实际支持的协议、模型与路径，不反复猜 /v1 或其他后缀。
如复用线上凭据，通过受保护的调用代理或 secret 注入使用，不读取并打印线上 secret。
工具实现 generate 与 revise；主 agent 提供审核结论，工具不自称能够调用当前聊天中的 Codex 审核模型。
第一阶段在活动 Work/Codex 会话中由主 agent 调用脚本、阅读结果并返修。未来若需无人值守，必须另行接入评审模型 API 与持久任务调度，不能声称聊天结束后本流程会自动运行。

## 最小任务记录
task_id、brief_version、相关设定版本/摘要、状态、模型配置（不含密钥）、调用次数、草稿路径、最佳稿路径、逐条审核问题、已通过 item_id、下一步。
状态：brief -> draft -> review -> revise -> approved；异常进入 blocked，可从记录恢复。
草稿单独保存，不自动进入公开 GitHub；只把通过稿、必要设计说明和脱敏状态提交。第三方仅接收用户授权的相关创作材料，不附带凭据、无关用户记忆或私密牌局数据。
任务记录与通过稿按项目既有存储方式持久保存；可重现临时内容留 scratch。

## 首次接通的验证
- 先检查配置和真实模型/协议，再发一条短创作请求，输出只显示正文与脱敏状态。
- 检查 generate/revise、长文截断、超时、认证错误、结果未知、费用熔断和断点恢复。
- 用一项真实酒馆文案完成“brief -> Gemini -> 主 agent 审核 -> 定点返修 -> 通过”的演练。
- 验证前不宣称 Gemini 已成功调用。纯开发文档/脚本不提升游戏版本；不因本设计部署 Worker。
