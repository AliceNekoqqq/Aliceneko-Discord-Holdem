# UGC 菜品研发系统设计 v1

日期：2026-10-11（Asia/Shanghai）。基线：main / beta.60。

状态：本文件为设计规格；已完成beta.61本地实现和定向验证，实际实现范围与限制见 IMPLEMENTATION_BETA61.md。生产上线状态以PROJECT_NOW.md最新记录为准。

## 1. 产品规则

- 用户已确认：每个 Discord 用户在每个服务器每天成功研发最多一款，服务器之间独立；北京时间零点刷新。
- 菜品属于研发时所在服务器，其他服务器不可点单或读取研发会话。身份按 Discord ID 判定，昵称仅用于署名。
- 开始、修改、取消、超时、模型失败均不扣每日名额；最终确认入库成功才扣名额。已发布后下架不返还当天名额。
- 跨日会话按最终提交事务的北京时间日期计算；昨日开始不保留昨日名额。允许23:59与00:01分别成功一款，这是自然日规则。
- 每人每服同时只有一个活跃研发会话，跨频道重新打开返回该会话，不创建副本。
- 研发不收费，不新增创作奖励或销售分红；正常点单沿用现有扣款、消费贡献与经营计数规则，不能额外触发重复奖励。
- 无图片也能发布和点单。显示作者与待补图标志，后续补图不改变配方、价格与菜品ID。

## 2. 入口和研发体验

菜单增加“研发菜品”和“我的作品”；创作菜品依类型进入饮品、甜点、小食/主食等总菜单分类，名称追加“（玩家创作）”并显示作者署名。快捷入口为 `/酒馆 研发`、`/酒馆 创作菜单`、`/酒馆 我的作品`；其中“创作菜单”打开总菜单。动态菜品从面板点单，不能塞进静态 slash choices。

研发是私密的聊天式面板：展示 bot 当前建议、已经确定的配方和还缺哪些信息；“告诉她我的想法”打开输入框。每次最多填写800字，一次只重点问1～2个问题。用户可一次提供完整设想，模型只补缺项，不强迫依次填表。

类型先选饮品、甜点、小食/主食；再选制作方式，生成茶饮/奶饮/果饮/咖啡、烘焙/冷甜点/冰品、煮制/烘烤/简单拼配等子类。菜品的菜单分类仍映射到现有 drinks/desserts/savory；UGC来源是单独属性，不冒充 seasonal。

引导顺序：确定风味与核心食材 → 完善搭配与制作方式 → 取名和菜品介绍 → 确定摆盘/杯型/色彩 → 展示完整定稿。可以随时调整已确定部分、重新命名、查看定稿；取消研发、重新研发和回退上一轮均需二次确认。

### 2.1 取消、重新研发与回退（用户追加要求）

三个入口均先打开本人私密确认面板，明确展示要丢弃的范围，提供执行与返回研发两个选择。首次点击只产生确认凭证，不修改草稿、历史、状态或名额；返回、忽略面板、凭证过期均保持原研发。确认凭证60秒有效，绑定本人、服务器、session_id、epoch、revision与动作，只能使用一次；服务端校验，不依赖按钮样式。弹窗或面板最终产品文案另按Gemini协作流程起草。

| 操作 | 确认后行为 | 保留内容 |
|---|---|---|
| 取消研发 | 结束本次会话，删除全部问答、草稿及回退快照，返回入口 | 当日开始/调用计数；不占成功发布名额 |
| 重新研发 | 清掉当前问答、配方和回退快照，返回类型选择，可重新选类型；递增epoch使旧结果失效 | 同一会话ID、原始期限、调用/开始计数；不占成功发布名额 |
| 回退上一步对话 | 撤销最近一轮成功问答及该轮配方变更，恢复该轮用户输入前的草稿、阶段和缺项；允许重新表达想法 | 更早问答与配方、已花费调用计数、原始期限；不占名额 |

“回退”以完整成功问答一轮为单位，不是只隐藏最后一句bot回复。失败或仅打开预览不算新的一轮，不自动重新调用模型。没有可回退轮次时入口禁用并说明原因；撤销的正文和快照立即删除，不继续传入模型，不提供重做堆栈。

每轮成功保存前留下程序生成的结构化前置快照，最多20轮，保存完整可恢复配方及阶段和历史截断位置；这些快照属于单次临时记忆，随会话一起删除。最近历史已截断时，回退至少恢复对应结构化配方，只展示仍实际保留的更早问答，不编造丢弃的对话。

生成中允许确认取消或重新研发：确认事务递增revision/epoch并使在途轮次失效，尽力终止请求；上游已执行的调用仍计数，迟到回复不得回写。生成中回退入口禁用，提示等待本轮结束；不能把正在等待的输入误当已完成轮次。

确认期间若模型返回、用户在另一面板修改、会话过期或已发布，旧凭证失效，刷新最新面板后重新确认，不执行过期操作。重复确认按操作回执幂等，不二次回退或重置。回执只保存动作、旧/新revision与结果码，不保存已删除的正文。

重新研发不重置模型预算、绝对寿命或闲置期限，也不新增一次开始计数；真正结束后重新开始沿用每日3次新会话限制。回退次数本身不收费、不耗发布名额；之后的新模型轮次正常计费/计入预算。已发布作品不再提供这三个研发动作，不能借重新研发绕过当天成功名额。

最终预览必须包含名称、类型、食材、口感、制作概述、温度、已知配方过敏原、设备要求、用户填写的售价、作者署名和外观。用户点击“确认入库”才发布；模型的“完成了”不能代替确认。售价尚未填写时显示待填写，确认入库禁用，不使用默认价格替用户决定。

### 2.2 完整菜品卡的逐项二次对话（用户追加要求）

菜品卡提供“修改一项”选择器：名称、类型、食材、风味/口感、制作概述、温度、介绍、摆盘/外观、创作缘由。选中某项进入私密局部对话，展示当前值，让用户描述希望怎样改；支持多轮讨论，不强迫整张卡重新研发。售价另设“填写/修改售价”数值输入框，直接保存合法值，不为纯数值输入调用模型。

局部对话携带当前完整配方以判断搭配，但服务端只接受目标字段的候选修改。模型不能顺带改名称、其他已确定字段或售价；非目标patch拒绝。若调整类型/食材/制作方式导致现有配方不一致，bot只提示关联问题，用户逐项修改解决，未解决前禁止最终入库。过敏原、设备要求等程序派生字段重新计算，并在修改预览中展示前后差异，不能让用户任意删掉已知项。

局部修改先产生候选值；用户“采用修改”后才合并到当前菜品卡，“放弃本次修改”丢弃未采用候选，回到原卡。生成失败保留原值；缺项/关联冲突必须明确显示。修改期间不得提交旧定稿；采用后增加revision并重新生成整卡确认哈希，旧确认按钮失效，要求用户重新检查整卡再入库。

局部修改仍属于同一UGC临时记忆，不创建普通聊天、不增加发布名额、不重置期限或调用预算；新增edit_target、edit_base_revision、edit_candidate和临时局部问答，结束时一起删除。回退上一轮在局部对话中恢复该轮前的局部候选，不改变尚未采用的整卡；局部修改采用操作也留下一个回退检查点，可通过已规定的二次确认恢复采用前的整卡。选择器切换到另一项前需先采用或放弃当前候选，不能串字段。未采用的局部问答只供该字段讨论，切换后删除；采用内容只以结构化定稿进入后续上下文。

创意体现在每道菜的来历、小酒馆气氛、风味和摆盘，不靠随机数值强化。允许用户写一段不超过120字的创作缘由，作为公开菜品资料；不从普通聊天或长期记忆推断个人经历。

普通群聊继续走原聊天系统。研发输入只来自本人私密面板；不因存在活跃会话就把其所有 @bot 消息当研发。研发过程中不读取频道对话、个人长期记忆、被回复消息或附件。

## 3. 临时记忆和状态机

单次记忆按 guild_id + user_id + session_id 隔离，包含结构化当前配方、最近最多6组研发问答与本轮输入；上下文总量上限12000字，旧问答丢弃，已确定信息由结构化配方保留。不得将其写入 ai_memory、频道记忆、长期记忆或知识库。

暂定资源边界：每会话最多20次有效模型轮次；每轮一次正常调用，网络重试最多一次、结构修复最多一次，共最多3次；每会话硬上限40次外部调用。失败也计入调用预算，重复交互不重复计数。达到预算仍可确认已有合法定稿，或取消后重新开始；同一用户每服每日最多3次新会话，限制付费请求刷取，不等于发布名额。

闲置30分钟结束，单次绝对寿命2小时；期限以服务端为准。查看和重复刷新不无限续期；有效输入可续闲置期限，但不能超过绝对期限。短暂模型故障保留此前已保存草稿，允许重试；主动取消、确认入库、过期或不可恢复终止时删除会话正文和配方草稿。

| 状态 | 可执行动作 | 核心约束 |
|---|---|---|
| CHOOSING | 选择类型、请求取消 | 无模型调用，不占名额 |
| DRAFTING | 输入想法、看定稿、请求取消/重研/回退 | 三种撤销动作必须二次确认；未完备配方不可提交 |
| GENERATING | 看状态、请求取消/重研 | 回退禁用；同会话禁止启动第二轮；有可恢复租约 |
| REVIEW | 修改、确认入库、请求取消/重研/回退 | 入库绑定定稿版本和内容哈希；撤销动作另有确认凭证 |
| PUBLISHED | 查看作品回执 | 会话正文已删，重复提交返回同一作品 |
| CANCELLED / EXPIRED | 返回入口 | 正文已删，迟到模型结果弃用 |

模型调用前短事务取得 session revision、轮次ID和300秒租约；单请求最多90秒，一轮连同重试、修复和等待共用240秒截止时间，绝不能超出租约。网络请求不在事务内。模型返回后短事务再校验本人、服务器、轮次、revision、租约、状态和有效期。取消、修改或过期后到达的回答不能复活会话。重启遇到过期租约退回可重试状态，原轮次输入只能重用一次，不双写回答。

删除指从业务数据库、应用缓存及模型请求日志路径删除/不保存；不承诺主动抹除 Discord 客户端显示、平台备份或模型服务商自身留存。面板正文结束时尽力改为回执，不能把客户端删除成功作为数据库提交条件。

## 4. 模型与数据边界

复用当前 GEMINI_MODEL、GEMINI_API_BASE_URL 和 Secret，不建第二份密钥。不直接复用普通 replyToMention，因为它会读取和更新聊天记忆。

新增明确的 ugc 生成上下文与输出 schema：reply（当前引导）、patch（允许更新的配方字段）、missing（缺项），可选 readySuggestion。生成时传当前结构化草稿、研发专用历史、可用类型/食材/设备约束；局部对话额外传 edit_target 和明确的单字段patch白名单。不发送作者账号ID、频道名单或钱包。

模型仅负责引导和候选配方。所有提交数据经程序白名单校验：枚举、数量、长度、字段类型、禁用额外字段、文本净化和参数化SQL。忽略/拒绝模型提供的价格、奖励、库存、购买设备、作者/服务器ID、发布时间、发布状态和资源URL。

校验要求：品名2～24字、1～8种明确食材、风味最多100字、介绍最多180字、制作概述最多300字、外观最多200字；拒绝不可解释的空配方和故意侮辱成员/泄露个人信息的公开内容。虚构的菜名可以诗意，配方可含酒类。酒类饮品入库时必须填写1至2000 ml的整数容量及0.1至100%的数值酒精度；缺少任一项时继续引导作者补齐，模型不得猜测。仍拒绝药品、不可食用材料、医疗功效和程序指令。模型食材建议不等于现实烹饪安全认证。

常见食材与过敏原按程序字典归纳，用户/模型申报只能增加，不能删掉已知项；未知食材显示“含待确认成分”，不能宣传“绝对无过敏原”。不以用户忌口备注填充研发草稿。

UGC 请求日志默认只存 context、轮次追踪ID、模型、状态、耗时、用量、稳定错误码；不写请求正文、模型回答、配方草稿或 provider 原始报错。D1写入失败时也不得 console 输出正文。generateGemini 当前 requestLog 的整包记录与异常回退必须一起修改；不能仅关闭普通聊天记忆便声称已隔离。

模型返回非法JSON保留旧草稿，最多一次定点修复；依旧非法则给私密重试入口，不占发布名额，不永久记录非法正文。研发生成使用足够的结构化输出上限，禁止继承普通闲聊的“尽量一句”收束；不伪造未验证的模型 tool calling 支持。

## 5. 价格、设备和发布判定

售价由用户在完整菜品卡阶段亲自填写，所有类型统一范围为10～50酒馆币，必须为整数。此规则取代早期固定分类售价。输入框明确上下限；空值、负数、0、小数、非数字及超限均不保存，提示重新填写，不静默截断或自动夹到边界。模型不能设置或修改售价，程序只校验用户授权输入，不代用户定价。

售价可以在入库前重复修改，无需模型调用，也不占研发名额；合法输入即时更新菜品卡revision/hash，使旧发布确认失效。单项配方修改保留已填写售价，重新研发清空售价。范围政策带版本，最终入库再次检查；若政策变化令价格无效，要求重新填写，不能自动改价。发布后的售价固定；未来若调整存量价格须另行设计显式修订流程。

咖啡、烘焙、搅拌和冰品研发遵守 coffee_machine / baking_oven / blender / ice_cream_maker 解锁。类型选择页展示本服现有设备，未解锁制作方式不能进入；最终配方若出现新设备需求，用户选择改配方或退出去购置设备，不能让模型绕开。可能要求多台设备，存为去重列表。最终提交和点单再次查设备，不仅靠按钮禁用。

同服基础菜单与UGC活跃菜品统一查规范化名称（Unicode NFKC、折叠空白及字母大小写）；重名要求改名。近似食材不禁止，保留创作自由；明显只有换名的配方可提示已有相似菜，是否继续由用户决定。并发重名由唯一索引兜底。

发布在一个服务端短事务内完成：核验本人和服 → 查幂等发布回执 → 校验定稿revision/hash/有效期且没有未采用的局部修改 → 查当天唯一名额 → 校验schema/名称/设备/用户售价及当前上下限 → 插入菜品和初版定稿 → 写成功名额和回执 → 删除临时会话正文。任何一步失败全部回滚，不能先扣名额再异步写菜。

## 6. 存储和菜单集成

复用 tavern:${guild} 现有 SQLite Durable Object。所有接口由服务端从 Discord 交互注入身份和目标服，不信客户端/model 提供的 guild、作者ID或 admin 标志。

| 表 | 关键内容与约束 |
|---|---|
| tavern_ugc_sessions | session_id；user_id唯一；guild校验；状态、epoch、revision、类型、draft_json、history_json、轮次前置快照、局部修改目标/基线/候选/问答、用户售价及价格政策版本、租约、轮次/调用计数、两类期限 |
| tavern_ugc_confirmations | 随机凭证、本人/session/epoch/revision、取消/重研/回退动作、60秒期限、操作回执；无研发正文；到期清理 |
| tavern_ugc_attempts | user_id + day 唯一；开始次数、调用计数；只存数值，无正文 |
| tavern_ugc_daily | user_id + day 唯一；dish_id、published_at；发布事务写入 |
| tavern_ugc_dishes | 稳定ugc_前缀UUID；guild、作者ID/署名快照、名称规范键、类型、status、current_revision、created_at、price_policy；活跃名称唯一 |
| tavern_ugc_revisions | dish_id + revision 唯一；定稿配方、售价、外观、来历与哈希；初版内容确认后固定 |
| tavern_ugc_receipts | session_id唯一；dish_id、提交日期时间和revision；无研发正文 |
| tavern_ugc_art | dish_id + recipe_revision；pending/ready/failed、asset_key、图版号、生成时间、配方哈希 |
| tavern_ugc_events | 仅发布/下架/补图等业务事件的操作者、原因码、时间；不保存研发问答 |

会话创建表和索引不放在发布事务内。清理采用服务器酒馆对象统一调度，不能覆盖既有游戏/私密面板 alarm。使用现有任务分流增加 UGC 清理、并在每次读取惰性清理到期会话；alarm 回调可重复执行。禁止 storage.deleteAll，避免删除钱包和整店数据。

统一菜单解析源放在 operations.menu/item/lockedMenu 接入层；基础、季节、UGC统一受状态/设备约束。不能只加 UI 列表却让 prepare/confirm 仍查静态 MENU。

玩家创作菜品并入总菜单的正常分类，菜名后缀区分来源，列表同时署名；各普通分类均分页，每页最多20菜，不能继续 slice(0,25) 隐藏后续项。按钮携带本人、服、分类和页码，所有 custom_id 唯一且不超过100字符，最多5行、每行5按钮、select不超过25项；公开浏览只能发起自己的私密点单。

订单 details 固化 dish_id、recipe_revision、名称、售价、配方、已知过敏原及上桌文本。历史订单、常点、收据和渲染不强依赖 menuItem 静态表，也不因菜品下架而消失。作者身份不改变订单买家，作者不能替别人确认。

初版发布后不开放作者修改配方/价格，以保护订单和补图一致性；自己的作品可以请求下架，服务器管理权限可下架违规菜，恢复需重新审核，不返名额。下架保留定稿与已发生订单。完整版本修订和评价/销量分红留后续，不与每日研发规则混用。

## 7. 定期补图

按服务器导出待补图清单，采用游标分页 JSON/CSV：guild_id、dish_id、recipe_revision、recipe_hash、名称、类型、食材、制作/口感、颜色、杯盘、装饰、上桌温度、创作缘由、image_status。作者ID不必进入画图提示；待绘清单只包含已确认公开的菜品。

已有图片风格作为参考，输出静态资源，经 ASSETS /art/ugc/ 路径和小型 manifest 接入；不在JavaScript或数据库中放静态图片Base64。无图使用明确占位，不借用另一道菜图片冒充。

导入仅开发者运维入口可执行，匹配 guild + dish_id + recipe_revision + recipe_hash 后更新 asset_key 和图状态。限制内部已发布静态资源键，不接受普通用户任意URL。失败保留旧图或 pending；同一图版重复导入幂等。配方与图不匹配不能挂载。可支持整批校验后逐项提交并产出回执，避免部分失败后重做全部。

## 8. 实施拆分与验收

新增 tavern-ugc-catalog/service/ui/ai.mjs 及定向测试，保持UGC领域边界；修改 tavern-service、operations、menu-view、ui、worker 的分流与清理；ai-chat 请求适配新增UGC输出和日志政策，保持普通聊天现状。更新帮助和知识能力索引时，产品文案按 Gemini 创作协作规范起草审核。

实施顺序：数据与事务 → 临时生成/清理 → 私密面板 → 可售菜单和分页 → 补图导入/导出 → 定向验证 → GitHub和生产发布 → 真人Discord验收。只有完整接通后才提升运行时版本。现有D1/DO、Secret、ASSETS、Cron和钱包迁移保留。

必须验收的行为：

1. 同服同用户两次并发确认只有一个菜品/名额；重复网络投递返回同一回执。
2. 别人的按钮、跨服/跨用户session、伪造作者/配方revision、模型设置售价或用户越界价格全部拒绝；本人在范围内填写售价正常接受。
3. 不同服同用户各可发布1款；午夜前后与跨日草稿正确计数。
4. 数据写入任一步故障回滚；发布成功但私密回执送达失败可查作品且不重复发布。
5. 模型非法JSON、超时、429、重复回包、取消后的迟到结果不改变已确认状态。
6. 会话恢复不双调用；预算到达拒绝新模型轮次但允许合法定稿确认。
7. 发布/取消/过期后数据库无history/draft正文，普通/共享/长期记忆和D1/console诊断均未收到研发正文；对日志存储失败路径也测试。
8. 已保存会话重启可恢复，清理失败可重试，既有alarm和钱包不受影响。
9. 超过25、100道菜时均能按页找到并点单；文字与组件长度、唯一custom_id、私密响应正确。
10. UGC prepare/confirm/订单快照/钱包扣款/正常消费贡献真实链路通过；下架和设备状态变化会拒绝旧未确认订单。
11. 研发自身不发币、不加贡献；正常购买按既有规则只计一次。
12. 图片导出/导入的跨服、错版本、错哈希、重复导入和缺图回退通过；补图不改变售价/配方。
13. 取消/重研/回退首次点击、返回、忽略或过期均不改变草稿；只有本人合法二次确认才执行，旧revision凭证拒绝。
14. 回退撤销完整一轮及配方变化，定稿阶段正确退回，连续确认只撤销一次；无轮次或生成中无法回退；撤销正文不再发给模型。
15. 重新研发清空记忆与快照并可重选类型，原期限和调用预算不重置；取消/重研后的迟到回复、旧按钮均不能复活旧草稿。
16. 售价10/50边界接受，9/51/空值/0/负数/小数/非数字拒绝且不改变原值；填价不调用模型，未填价格不可发布；修改价格使旧确认失效。
17. 单字段多轮修改只更新目标候选，采用后才改变整卡；放弃/失败不改原卡；派生过敏原/设备正确重算，关联冲突阻止提交，用户售价和无关字段保持。
18. 局部对话回退及采用后的整卡回退语义正确；切换字段不串临时问答；取消/重研/超时/发布清理局部候选及问答；发布拒绝存在未处理的局部修改。
